# 第一幕 · 皇帝的怪命令与五只锦囊

> **给小朋友的话：**
> 这是一个关于“操作系统”的童话。别怕那些古怪的名词。故事里的剧场，就是一台计算机；舞台，就是处理机；戏班，就是进程；演员，就是线程。等故事讲完，我们再翻开后面的“说明书”，你会发现，原来那些名词都藏在这个故事里。
>
> **给大朋友的话：**
> 第一幕对应“进程与线程”。故事之后的“长大了后您会怎么叙述这个故事”部分，按教材口径严格化，并标出考点、易错点和补充知识。可以先读故事，再读说明书；也可以反过来。

## 第一场 台伯河畔的大剧场

很久很久以前，在台伯河畔，有一座大剧场。

它的台阶是白色的，像一排排刚洗过的牙齿；它的圆顶是金色的，太阳一照，全罗马都能看见。皇帝奥古斯都一世最喜欢来这里看戏。他坐在最中间的包厢里，怀里抱着一袋蜜饯，看得正高兴。

忽然，一个戴着铃铛帽的弄臣翻着跟头进来，叮叮当当，像一只会走路的风铃。

“陛下，陛下！”弄臣说，“您不觉得，一次只看一出戏，太寂寞了吗？”

皇帝嚼着蜜饯：“寂寞？舞台上一会儿打仗，一会儿谈恋爱，热闹得很。”

弄臣摇摇头：“可是，我想看《金苹果》里的大力士，也想看《狼奶》里的双胞胎，还想看《尼罗河上的月亮》里的船。为什么他们不能同时演呢？”

皇帝的眼睛亮了。他把蜜饯袋一扔：

“好！传我的命令：大剧场必须在同一个时间段里，演出不同的戏！”

弄臣又补了一句：“还有，剧本要密封。演员上台才能拆开自己那一页，管理员不许偷看。谁偷看，谁就去扫马厩！”

皇帝觉得这个主意很有趣：“准了！”

命令传到剧场后台，管理员马库斯差点从梯子上摔下来。

他手里攥着三卷用红蜡封住的剧本，像攥着三块烫手的石头。

“一座舞台，三出戏，还不许看剧本？”马库斯喃喃地说，“这不是让我闭着眼睛给狮子梳头吗？”

---

## 第二场 管理员的三个难题

马库斯先试了第一个笨办法：让三个戏班一起上台。

结果，大力士撞倒了双胞胎，双胞胎踩到了尼罗河的船，船上的月亮道具又砸中了大力士的脚。三个戏班在舞台上挤成一团，台词串得乱七八糟。观众先是愣住，然后笑得前仰后合。

皇帝不高兴：“我要看三出戏，不是看一锅粥！”

马库斯又试了第二个笨办法：让一个戏班从头演到尾，另外两个戏班在旁边等。

结果，《金苹果》演到第三幕，皇帝已经打了十个哈欠；《狼奶》还没上场，弄臣已经开始在包厢里翻跟头；《尼罗河上的月亮》的演员干脆靠着道具睡着了。

马库斯还想试第三个笨办法：偷偷拆开剧本看一眼。

他刚把蜡封抠出一个小口，皇家卫兵就从天而降，把他请去扫了一天的马厩。

马库斯垂头丧气地回到后台。他想：

“我看不懂剧本，演员也不能提前知道整个剧本，皇帝还要三出戏同时演。这可怎么办？”

就在这时，门口传来一阵驼铃声。

三位从东方来的博士，跟着一颗亮晶晶的星星，走进了剧场。他们一个高，一个胖，一个安静，背着三只旧行囊。

马库斯像抓住了救命稻草：“三位先生，你们会读剧本吗？”

高个子博士摇摇头：“不会。”

“那你们会演戏吗？”

胖博士笑了：“也不会。”

马库斯快哭了：“那你们会什么？”

安静的博士说：“我们会把一件大难题，拆成几件小难题。我们会告诉你，怎样管理一群你读不懂的戏班。”

他从包里拿出一个木匣，匣子里躺着五只锦囊。

“遇到什么难题，就拆哪一只。”

---

## 第三场 第一只锦囊：班牌与戏班

马库斯拆开第一只锦囊，里面掉出一块小木牌和一本空白账簿。

博士说：“先别管剧本。剧本是死的，戏班是活的。”

他在木牌上写下几行字：

- **剧本**＝程序
- **戏班**＝进程
- **舞台**＝处理机
- **管理员**＝操作系统

“剧本放在箱子里，你不去碰它，它不会自己演。”博士说，“戏班穿上戏服、搬来道具、走上舞台，这件事才叫演出。程序是静态的，进程是动态的；程序是纸上的字，进程是正在发生的戏。”

马库斯问：“那我要怎么管这些活蹦乱跳的戏班呢？”

博士把木牌翻过来：“给每个戏班发一块**班牌**。班牌就是它的身份证，也是它的现场记录。”

班牌上要写四样东西：

1. **身份**：班号、父戏班、主人是谁。
2. **调度**：现在是什么状态、优先级多高、等了多久、已经用了多少舞台时间。
3. **资源**：用了哪些道具、穿了哪些服装、占了哪间化妆间、打开了哪些门（文件）、占着哪块大屏（I/O 设备）、剧本和道具放在哪里。
4. **现场**：舞台上的灯位、演员站位、剧本书签、台词念到哪一句。

“这块班牌，”博士说，“就是操作系统里的 **PCB（进程控制块）**。它必须放在管理员办公室里，随时能查到，不能丢。**班牌在，戏班就在；班牌丢了，戏班就散了。**”

马库斯赶紧把这句话记在账簿上。

博士又带他参观戏班的后台。后台有五个房间：

- **剧本间**：放着台词和舞台指示，对应程序段（`.text`、`.rodata`）。
- **自备道具间**：放着戏班自己带来的道具，对应数据段（`.data`、`.bss`）。
- **临时道具架**：演到一半需要什么，就去借什么，对应堆（`malloc`）。
- **台词栈**：记着演员从哪一句来、该回哪一句去，对应栈。
- **管理员办公室**：放着班牌和内核栈，演员不能随便进，对应内核区。

马库斯明白了：“原来我不需要知道剧本讲了什么，我只需要知道每个戏班需要什么、演到哪、现在是什么状态。”

博士点点头：“对了。操作系统也是这样。它不读懂你的程序，它管理你的进程。”

## 第四场 第二只锦囊：五道门

第二只锦囊里是一张地图，画着五道门。

博士说：“一个戏班，不是想上台就能上台的。它要走过五道门。”

1. **新建门（创建态）**：新戏班来登记，领班牌，分化妆间。它还不能上台。
2. **候场门（就绪态）**：万事俱备，只欠舞台。戏班在候场区排队。
3. **上台门（运行态）**：管理员叫到它，它才能上台。
4. **等道具门（阻塞态）**：演到一半，需要大屏、道具，或者等别的戏班的信。戏班自己去等道具区排队。即使舞台空着，它也不能上台。
5. **谢幕门（终止态）**：戏演完了，或者戏班解散了。还道具，交班牌。

博士用粉笔在墙上画箭头：

- 新建 → 候场：登记完，进入候场区。
- 候场 → 上台：管理员叫到它。
- 上台 → 候场：演出时限到了，或者被更紧急的戏挤下台；戏还没演完，只是下台候场。
- 上台 → 等道具：需要道具或者等事件；这是戏班自己去的。
- 等道具 → 候场：道具到了，或者事件发生了；这是别人通知的。它必须先回候场区，不能直接上台。
- 上台 → 谢幕：戏演完了。

博士竖起三根手指：

“记住三句话：

第一，**等道具的，不能直接冲上台**。

第二，**候场的，不能直接去等道具**。

第三，**上台是管理员叫的，等道具是自己去的，道具到了是别人通知的**。”

马库斯问：“为什么等道具的不能直接上台？道具都到了呀！”

博士说：“道具到了，只是它具备了上台的条件。可舞台上可能还有别的戏班在演。它得先回到候场区，和大家一起排队，等管理员叫它。这就叫：**阻塞态不能直接变运行态，必须先变就绪态**。”

马库斯又问：“那候场的为什么不能直接去等道具？”

博士笑了：“它还没上台，怎么知道道具不够呢？它必须先上台，演着演着发现缺道具，才能去等。这就叫：**就绪态不能直接变阻塞态**。”

马库斯把这三句话写在班牌背面，每天念三遍。

博士还告诉他：“戏班去等道具，是它自己知道的，叫**主动**；道具到了，是别人通知的，叫**被动**。上台和下台，是管理员安排的，也是被动。你以后出考题，就爱考这个。”

马库斯没听懂“考题”是什么，但他把“主动”“被动”记了下来。

## 第五场 第三只锦囊：四道金牌

第三只锦囊里是一面铜锣和四块金牌。

博士问：“你现在管着五道门，最怕什么？”

马库斯说：“最怕两个戏班同时挤进一个门，账本对不上。”

博士敲了一下铜锣：“咚——”

整个后台的人都定住了，连一只飞过的蛾子都停在半空。

“这叫**原子操作**。”博士说，“你敲锣的时候，谁也不能动。你趁这个时候改班牌、换队列，改完了再敲一下，大家才继续。这样就不会有两个戏班同时改同一本账。”

四块金牌上各写着一件事：

**第一块：创建**

1. 申请一块空白班牌，分配班号。
2. 分配必要的资源。
3. 填写班牌：现场、调度信息、资源清单。
4. 把戏班插入候场队列，等待上台。

**第二块：终止**

1. 按班号找到班牌。
2. 如果它还在台上，先请它下台，再安排别的戏班。
3. 归还道具，关闭文件。
4. 处理父子戏班：是“连坐”一起解散，还是“托孤”给别人养。
5. 收回班牌。戏班从此不存在。

**第三块：阻塞**

1. 戏班自己知道要等道具或者等事件。
2. 把舞台现场保存到班牌里。
3. 把状态改成“等道具”，插入等道具队列。
4. 让管理员安排别的戏班上台上。

**第四块：唤醒**

1. 按编号找到等道具队列里的班牌。
2. 把它从等道具队列里移出来。
3. 把状态改成“候场”。
4. 插入候场队列。

博士特别叮嘱：“**阻塞和唤醒，必须成对使用。** 就像门铃和开门：只按门铃不开门，客人会在门口等一辈子；只开门不按门铃，门自己开了，会吓死人。”

马库斯把这四块金牌挂在办公室墙上。每次操作前，他都先敲一下铜锣。

## 第六场 第四只锦囊：四条传信路

第四只锦囊里装着四样小东西：一块白板、一个信箱、一截传声筒、一只门铃。

“三个戏班要合作。”博士说，“《金苹果》需要《狼奶》送来的金苹果；《尼罗河上的月亮》需要和《金苹果》共用大屏；演员们还要互相提醒什么时候上场。他们得说话。”

**第一条路：共享白板**

“这是最快的方法。大家在院子里看同一块白板，谁都能写。可是，如果两个戏班同时写，字就叠在一起，谁也看不清。所以要有规矩：一个人写的时候，另一个人等。”

博士说：“这叫**共享存储**。它最快，最适合传大东西，但必须同步互斥，不然白板会被涂成一团。”

**第二条路：信箱**

“把信送到对方的信箱，或者送到一个公共邮箱。邮差会帮你送。好处是你们不用见面；坏处是邮差要跑腿，信多了会慢。”

博士说：“这叫**消息传递**。直接写给某个戏班，叫直接通信；写到公共邮箱，叫间接通信。它让戏班之间解耦，适合分布式，但内核复制消息有开销。”

**第三条路：传声筒**

“一根管子，从这头说话，那头听。同一时间只能一个方向说，叫**半双工**。管子里没有纸条，读的人就得等；纸条塞满了，写的人也得等。”

博士说：“这叫**管道**。它是字节流，有缓冲区。读空会阻塞，写满也会阻塞。匿名管道通常给父子戏班用；命名管道有名字，没有亲缘关系的戏班也能用。”

**第四条路：门铃**

“按一下，对方就知道有事。可是门铃只能‘叮咚’一声，不能送一筐苹果。它适合报信，不适合送大件。”

博士说：“这叫**信号**。它是异步通知，像软中断。它能告诉戏班‘道具到了’‘该谢幕了’，但带不了大量数据。”

胖博士补充：“如果两个剧场在很远的城市，还可以用信鸽。那叫**套接字（Socket）**，是网络里的通信方式。”

马库斯问：“哪一种最好？”

博士说：“没有最好，只有最合适。共享白板最快，但最需要规矩；信箱最解耦，但有邮差的开销；传声筒最简单，但会堵；门铃最轻，但只能报信。”

## 第七场 第五只锦囊：演员的分身术

第五只锦囊里是一本小本子和一张画着小人儿的图。

戏班抱怨：“一个演员怎么同时演三个角色？我们需要更多演员！”

博士说：“一个戏班，当然可以有很多演员。**演员才是真正上台表演的人。**”

他在图上画了一个大圆圈，里面画了三个小人儿：“大圆圈是戏班，小人儿是演员。演员共享戏班的剧本、道具、化妆间和工钱；但每个演员有自己的小本子，记着自己演到哪一句、站在哪里、下一句是什么。”

马库斯问：“这个小本子叫什么？”

博士说：“叫 **TCB（线程控制块）**。戏班有班牌 PCB，演员有小本子 TCB。”

博士又画了三张图，讲三种管演员的办法。

**第一种：让班主自己管演员。**

管理员只看见戏班，看不见演员。班主说“张三上”，张三就上；班主说“李四上”，李四就上。

“这叫**用户级线程**。好处是换演员快，不用跑管理员办公室；坏处是，如果张三在台上等道具，管理员以为整个戏班都在等，就把整个戏班晾在一边。而且，一个戏班只能在一座舞台上演，不能同时上两座舞台。”

**第二种：给每个演员发班牌。**

管理员亲自管每个演员。张三等道具，李四可以继续演；张三上第一座舞台，李四上第二座舞台，真正同时。

“这叫**内核级线程**。好处是灵活、能并行；坏处是每次换演员都要跑办公室，手续多，开销大。”

**第三种：组合起来。**

给每个戏班发几块“台柱”班牌，每个台柱再管几个演员。

“这叫**多对多模型**。它取长补短，但最复杂。”

博士画了一张表：

| 模型 | 怎么映射 | 特点 |
|---|---|---|
| 多对一 | 很多演员 → 一个台柱 | 快，但一个等道具，全戏班等；不能上多座舞台 |
| 一对一 | 一个演员 → 一个台柱 | 能并行，阻塞灵活；但台柱太多，办公室忙不过来 |
| 多对多 | n 个演员 → m 个台柱 | 取长补短；实现复杂 |

马库斯选择了多对多：每个戏班留三个台柱，每个台柱带几个演员。这样，既能快，又能同时上多座舞台。

博士提醒他：“记住，**戏班是资源的家，演员是执行的兵。班牌只有一个，小本子每人一本。**”

## 第八场 首演之夜

首演之夜，大剧场灯火通明。

马库斯用五只锦囊，把三个戏班安排得井井有条：班牌挂在办公室，演员拿着小本子，后台的白板、信箱、传声筒、门铃都准备好了。

可是，只有一座舞台，怎么同时演三出戏呢？

马库斯让三个戏班轮流上场：《金苹果》演一小段，下台；《狼奶》演一小段，下台；《尼罗河上的月亮》演一小段，下台；再轮到《金苹果》。

观众看得眼花缭乱，以为三出戏在同时进行。

博士说：“这叫**并发**。一段时间内交替执行，宏观上像同时。”

皇帝看得高兴，忽然指着窗外：“看！我让人又建了两座舞台！明天，三座舞台同时开演！”

马库斯愣了一下，随即笑了：“那就是**并行**——同一时刻，真正同时。”

博士点点头：“对。并发是轮流，并行是真正同时。三座舞台，就是三个处理机。”

皇帝又问：“可是，谁先上台？演多久？如果有戏班等了一整天，怎么办？”

马库斯看向第二只锦囊匣。匣子上写着两个字：“调度”。

弄臣又凑过来，叮叮当当地说：“还有，如果两个戏班同时抢同一件道具怎么办？”

马库斯叹了口气。博士们笑了：“那是下一个故事了。”

大剧场的灯一盏盏熄灭。马库斯把今天的规则写进《剧场法典》。他知道，明天还有新的难题。但只要记住：先看清楚目标，再选择规则；没有完美的办法，只有合适的办法。

## 1. 进程是什么

### 1.1 定义

**进程是进程实体的运行过程，是系统进行资源分配和调度的一个独立单位。**

更通俗地说：

> **进程是程序的一次执行实例。**

也有人把它描述为：

> 程序加载到内存后，CPU 执行这个程序的过程；或者，具有独立功能的程序在一个特定数据集合上的执行活动。

这些说法不神秘，核心都在说三件事：

1. 它**正在运行**；
2. 它具有某种**独立功能**；
3. 它是系统分配资源和调度的**基本单位**。

### 1.2 进程实体

进程实体（也叫进程映像）通常由三部分组成：

1. **程序段**：机器指令、只读数据，如 `.text`、`.rodata`；
2. **数据段**：已初始化/未初始化数据，如 `.data`、`.bss`；
3. **PCB**：进程控制块，常驻内存，记录进程状态和现场。

> **【考点】** 进程实体＝程序段＋数据段＋PCB。  
> **【考点】** PCB 是进程存在的唯一标志，不是程序代码。

### 1.3 进程的特征

1. **动态性**：进程是程序的一次执行，有生命周期，有创建、运行、终止。动态性是最根本的特征。
2. **并发性**：多个进程在一段时间内交替执行。
3. **独立性**：进程可以独立运行、独立获取资源，是资源分配和调度的基本单位。
4. **异步性**：进程走走停停，推进速度不可预知；不同执行顺序可能产生不同结果。

> **【易错】并发 vs 并行：**
> - **并发**：一段时间内多个进程交替执行，宏观上“同时”，微观上同一时刻只有一个在跑（单处理机）。
> - **并行**：同一时刻多个处理机上真正同时执行。
> - 并行能更好地实现并发，但并发不一定需要并行。
>
> 这里特别提醒：并发和并行很容易说反，以这里为准。

### 1.4 进程与程序的区别

| 对比 | 程序 | 进程 |
|---|---|---|
| 状态 | 静态 | 动态 |
| 生命周期 | 可长期保存 | 有创建、运行、终止 |
| 数量关系 | 一个程序可对应多个进程 | 一个进程对应某次执行 |
| 组成 | 指令、数据 | 程序段、数据段、PCB |
| 标志 | 文件 | PCB |
| 资源 | 运行前不占有 CPU、内存等运行资源 | 占有 CPU、内存、I/O 等资源 |

> **【考点】** 程序是静态的，进程是动态的；程序可以长期保存，进程有生命周期；一个程序可以对应多个进程，一个进程只对应某次执行。

### 1.5 引入线程后的补充

在传统操作系统里，进程既是**资源分配单位**，又是**调度单位**。

引入线程后，通常说：

- **进程是资源分配的基本单位**；
- **线程是 CPU 调度和执行的基本单位**。

> **【考点】** 做题时要看题目语境：  
> - 未引入线程的传统 OS：进程是资源分配和调度的独立单位。  
> - 引入线程后：进程是资源分配单位，线程是 CPU 调度和执行单位。

## 2. PCB：进程的“班牌”

### 2.1 为什么需要 PCB

操作系统不能直接管理静态程序，只能管理“运行中的进程”。它需要一种数据结构，记录进程的状态、标志、资源、CPU 现场等信息。这个数据结构就是 **PCB（Process Control Block，进程控制块）**。

- PCB **常驻内存**，由内核维护；
- PCB **不属于用户程序**；
- PCB 是进程存在的**唯一标志**；
- 进程切换时，要把当前进程的 CPU 上下文保存到 PCB，再从下一个进程的 PCB 恢复现场。

> **【考点】** PCB 是进程存在的唯一标志；PCB 常驻内存；PCB 由内核维护。  
> **【补充】** 实际系统中，为了节省内存，部分 PCB 信息可能被换出；但教材通常按“PCB 常驻内存”来考。

### 2.2 PCB 的内容

PCB 的内容可以记成四类：

| 类别 | 典型内容 |
|---|---|
| 标识信息 | PID、UID、PPID（父进程 ID） |
| 调度信息 | 状态、优先级、等待时间、已占用 CPU 时间、时间片 |
| 资源信息 | 打开文件 fd、I/O 设备、代码段/数据段/堆栈指针、内存管理信息 |
| CPU 状态 | 通用寄存器、PC、栈指针、程序状态字等现场 |

用故事里的话说：

- 班号、主人、父戏班＝标识信息；
- 状态、优先级、等了多久＝调度信息；
- 道具、服装、化妆间、大屏＝资源信息；
- 灯位、站位、剧本书签＝CPU 状态。

### 2.3 PCB 的组织方式（补充）

PCB 通常放在内核的 PCB 表里。常见的组织方式有：

1. **链接方式**：把同一状态的 PCB 用链接字串成队列，如就绪队列、阻塞队列。
2. **索引方式**：为每种状态建立索引表，索引表项指向对应的 PCB。

> **【补充】** 考试偶尔会问 PCB 的组织方式；记住“链接”和“索引”两种即可。

### 2.4 进程切换与上下文

进程切换时，操作系统要：

1. 保存当前进程的 CPU 上下文（寄存器、PC、栈指针等）到其 PCB；
2. 更新 PCB 状态，把 PCB 移入相应队列；
3. 选择下一个进程；
4. 从下一个进程的 PCB 恢复 CPU 上下文；
5. 必要时切换地址空间（进程切换通常要换页表，线程切换同进程内不用）。

> **【考点】** 进程切换要保存/恢复 CPU 上下文到 PCB；进程切换通常比同进程内的线程切换开销大，因为要切换地址空间。

## 3. 进程的内存布局

一个经典的用户进程“舞台”大致包含：

- **程序段**：`.text` 指令、`.rodata` 只读数据；
- **数据段**：`.data` 已初始化数据、`.bss` 未初始化数据；
- **堆**：动态申请的内存，如 `malloc`，通常向上增长；
- **共享库映射区**：动态链接库等；
- **用户栈**：函数参数、局部变量、返回地址，通常向下增长，由系统管理；
- **内核区**：PCB、内核栈等，用户不能随意访问。

> **故事对照：** 剧本台词在程序段；自备道具在数据段；临时借道具用堆；演到哪、返回哪用栈；班牌 PCB 在后台内核区。

常见的 32 位布局大致是：

```text
低地址
┌────────────────────┐
│ 不使用/保留         │
├────────────────────┤
│ 程序段 .text/.rodata│
├────────────────────┤
│ 数据段 .data/.bss   │
├────────────────────┤
│ 堆（向上增长）       │
├────────────────────┤
│ 共享库映射区         │
├────────────────────┤
│ 用户栈（向下增长）   │
├────────────────────┤
│ 内核区（PCB、内核栈）│
└────────────────────┘
高地址
```

> 具体地址数值不用死背；记住“舞台里有什么、谁管理、往哪个方向长”更重要。部分操作系统把内核区放在低地址，布局相反，但组成部分不变。

## 4. 进程的五状态与转换

### 4.1 五种状态

1. **创建态**：进程正在被创建，PCB 已分配，但资源/初始化尚未完成。
2. **就绪态**：万事俱备，只欠 CPU。进程已获得除 CPU 外的所需资源，等待调度。
3. **运行态**：进程占有 CPU，正在执行。
4. **阻塞态**：进程等待某个事件（I/O 完成、信号量、消息等），即使 CPU 空闲也不能运行。
5. **终止态**：进程正在结束，资源被回收，PCB 将被撤销。

> 主线通常关注**就绪、运行、阻塞**三个基本状态；创建和终止是生命周期的两头。

### 4.2 状态转换

| 转换 | 条件 | 主动/被动 | 考点 |
|---|---|---|---|
| 创建 → 就绪 | 初始化完成，进入就绪队列 | 系统 | 创建后一般不能直接运行 |
| 就绪 → 运行 | 调度器选中，分配 CPU | 被动 | 候场演员被叫上台 |
| 运行 → 就绪 | 时间片到、被抢占 | 被动 | 还没杀青，只是下台候场 |
| 运行 → 阻塞 | 等待 I/O、信号量等事件 | **主动** | 演员主动去等道具 |
| 阻塞 → 就绪 | I/O 完成、事件发生 | **被动** | 道具到了，回到候场区 |
| 运行 → 终止 | 正常结束或异常 | 主动/异常 | 杀青 |

用 ASCII 图表示：

```text
              ┌────────┐   调度    ┌────────┐   结束   ┌────────┐
    创建 ───→ │  就绪  │ ───────→ │  运行  │ ───────→ │  终止  │
              └────────┘ ←─────── └────────┘          └────────┘
                   ↑          时间片到/被抢占  │
                   │ 唤醒                     │ 等待事件
                   │                          ↓
              ┌────────┐
              │  阻塞  │
              └────────┘
```

其中：

- 运行 → 就绪：时间片到/被抢占；
- 运行 → 阻塞：等待事件；
- 阻塞 → 就绪：事件完成（唤醒）；
- 就绪 → 运行：调度；
- 没有“就绪 → 阻塞”，也没有“阻塞 → 运行”。

### 4.3 必须记住的几条

1. **就绪不能直接变阻塞**：进程还没运行，不能发起 I/O 请求或等待事件。
2. **阻塞不能直接变运行**：即使等待的事件发生了，也要先回到就绪队列，等待调度器选中。
3. **运行 → 阻塞是主动的**：进程自己请求资源/IO，知道自己要等。
4. **阻塞 → 就绪是被动的**：由事件完成/中断唤醒，不是进程自己跳出来。
5. **运行 → 就绪是被动的**：时间片到或被抢占，进程本身还想继续跑。
6. **阻塞 → 就绪需要唤醒**：block 和 wakeup 必须成对使用。

> **【高频考点】** “阻塞态不能直接转换为运行态，必须先转换为就绪态。”  
> **【高频考点】** “就绪态不能直接转换为阻塞态。”  
> **【高频考点】** “运行态到阻塞态是主动的，阻塞态到就绪态是被动的。”

### 4.4 关于“挂起态”的预告

第二幕的中级调度会引入“挂起”：

- **就绪挂起**：进程在就绪状态，但被换出到外存；
- **阻塞挂起**：进程在阻塞状态，且被换出到外存。

挂起不是终止：PCB 还在，进程还在，只是暂时不在内存/剧场里。第二幕会详细讲。

## 5. 进程控制原语

### 5.1 什么是原语

**原语是不可中断、原子执行的基本操作。** 进程的创建、终止、阻塞、唤醒通常用原语实现，以保证关键操作的一致性。

> **【考点】** 原语不可中断，保证原子性。  
> **【补充】** 为什么必须原子？如果创建到一半被中断，PCB 可能不完整；如果阻塞/唤醒到一半被中断，进程可能同时出现在两个队列里，或者从队列里消失。

### 5.2 进程创建

1. 申请空白 PCB，分配 PID；
2. 分配必要资源（内存、I/O 等）；
3. 初始化 PCB：CPU 状态、调度信息、资源信息；
4. 插入就绪队列，等待调度。

> **【考点】** 创建后一般不能直接运行，要先进入就绪队列。

### 5.3 进程终止

1. 按 PID 查 PCB；
2. 若在运行态，剥夺 CPU，调度其他进程；
3. 释放资源、关闭文件；
4. 处理父子关系：级联终止（连坐）或托孤（孤儿进程被收养）；
5. 回收 PCB，进程消失。

> **【补充】** 进程终止的原因：正常结束、异常结束、致命错误、被其他进程杀死等。  
> **【易错】** 不是所有系统都“父死子必死”；有的系统会级联终止，有的会托孤。考试要看题目说明。

### 5.4 进程阻塞

1. 进程请求资源/IO，知道自己要等；
2. 保存 CPU 现场到 PCB；
3. 状态改为阻塞，插入阻塞队列；
4. 调度就绪队列中其他进程。

> **【考点】** 阻塞是进程主动的行为。

### 5.5 进程唤醒

1. 按编号找到阻塞队列中的 PCB；
2. 移出阻塞队列；
3. 状态改为就绪；
4. 插入就绪队列。

> **【考点】** 唤醒是被动的，由事件完成/中断触发。  
> **【考点】** block 和 wakeup 必须成对使用，否则可能永久阻塞或错误唤醒。

## 6. 进程通信（IPC）

进程有独立性，地址空间通常相互隔离，但又需要合作，所以需要**进程间通信（IPC）**。

### 6.1 四种常考方式

| 方式 | 故事里的比喻 | 关键点 | 优点 | 缺点/注意 |
|---|---|---|---|---|
| **共享存储** | 共享白板 | 划一块共享内存，进程读写 | 最快，适合大数据 | 必须同步互斥，需要协议 |
| **消息传递** | 寄信/信箱 | 直接通信指定对方；间接通信用邮箱/端口 | 解耦，适合分布式 | 内核复制有开销 |
| **管道通信** | 传声筒 | 半双工、字节流、缓冲区；读空/写满会阻塞 | 简单，适合父子进程 | 匿名管道通常需亲缘；命名管道可无亲缘 |
| **信号** | 按门铃 | 异步通知，携带信息少 | 通知事件 | 不传大量数据 |

补充：**套接字（Socket）** 常用于跨主机网络通信。

### 6.2 共享存储

进程共享一块内存。速度最快，适合传大量数据，但“白板”可能被同时涂改，必须用信号量/互斥锁同步。

- **基于数据结构的共享**：共享一个数据结构（如共享缓冲区）；
- **基于存储区的共享**：划出一块内存区域，进程直接读写。

> **【考点】** 共享存储最快，但必须同步互斥。

### 6.3 消息传递

- **直接通信**：`send(P, msg)`、`receive(Q, msg)`，明确发给谁；
- **间接通信**：发到邮箱/端口，发送者和接收者解耦。

消息由内核复制，适合结构化消息。优点是解耦、适合分布式；缺点是内核复制有开销。

### 6.4 管道

管道是内核缓冲区，按字节流。

- **半双工**：同一时刻通常单向；
- 读空会阻塞，写满会阻塞；
- 匿名管道常用于父子进程；
- 命名管道有名字，可让无亲缘进程通信。

> **【考点】** 管道是半双工、字节流、有缓冲区；读空/写满会阻塞；匿名管道通常需亲缘，命名管道可无亲缘。

### 6.5 信号

信号是异步通知，类似门铃/软中断，适合“通知事件发生”，不适合传大量数据。

> **【考点】** 信号异步、携带信息少；共享存储最快；消息传递解耦；管道半双工。

### 6.6 套接字（补充）

套接字用于网络通信，可跨主机。常见类型：

- **流式套接字（TCP）**：面向连接、可靠、字节流；
- **数据报套接字（UDP）**：无连接、不可靠、消息边界保留。

> **【补充】** 基础 OS 教材可能只提“套接字”这个名字；知道它用于跨主机通信即可。

## 7. 线程与多线程模型

### 7.1 线程是什么

**线程是程序执行流的最小单元，是 CPU 调度和执行的基本单位。**

引入线程后，常记：

> **进程是资源分配单位，线程是调度执行单位。**

一个进程可以包含多个线程。它们共享：

- 代码段；
- 数据段；
- 堆；
- 打开文件、I/O 等进程资源；
- 地址空间。

每个线程私有：

- 寄存器、PC；
- 私有栈；
- 线程 ID、状态、优先级；
- TCB（线程控制块）。

> **【考点】** 同进程线程共享代码、数据、堆、文件、地址空间；私有寄存器、栈、PC、TCB。  
> **【考点】** 线程是 CPU 调度和执行的基本单位；进程是资源分配的基本单位。

### 7.2 进程与线程对比

| 对比 | 进程 | 线程 |
|---|---|---|
| 资源 | 资源分配单位 | 共享所属进程资源 |
| 调度 | 传统上是调度单位 | CPU 调度执行基本单位 |
| 地址空间 | 独立 | 同进程线程共享 |
| 切换开销 | 大，要换地址空间 | 同进程线程切换小 |
| 私有内容 | PCB、地址空间等 | TCB、寄存器、栈、PC |
| 通信 | 需要 IPC | 同进程线程可直接读写共享数据，但需同步 |

> **【易错】** 不是“线程切换一定比进程切换快”。同进程内的线程切换不用换地址空间，通常更快；跨进程的线程切换仍可能涉及地址空间切换。考试一般说“同进程线程切换开销小于进程切换”。

### 7.3 用户级线程

线程的创建、切换、调度都在用户空间完成，操作系统只感知进程，不知道线程。

**优点：**

1. 切换开销低，不需要陷入内核；
2. 调度策略可由应用程序定制；
3. 与 OS 无关，可移植。

**缺点：**

1. 一个线程阻塞系统调用会导致整个进程挂起；
2. 多处理器上，同一进程的用户级线程不能真正并行（内核只把该进程当一个调度单位）；
3. 内核无法单独调度某个线程。

> **故事对照：** 管理员只知道整个戏班在演，不知道演员内部有几个分身；一个分身等道具，整个戏班被卡住。

### 7.4 内核级线程

线程的创建、切换、调度由内核管理，需要陷入内核态。

**优点：**

1. 多核可并行，不同线程可同时跑在不同 CPU 上；
2. 一个线程阻塞，其他线程仍可运行，阻塞处理灵活；
3. 内核可以单独调度线程。

**缺点：**

1. 切换需陷入内核，开销较大；
2. 线程数量受内核资源限制；
3. 实现更复杂。

### 7.5 组合实现与多线程模型

取长补短：用户级线程＋内核级线程，由内核线程支撑用户线程。组合实现需要**两层调度**：

- 用户态线程库把用户线程调度到内核线程上；
- 内核把内核线程调度到 CPU 上。

| 模型 | 映射 | 特点 | 考点 |
|---|---|---|---|
| **多对一** | 多用户线程 → 1 内核线程 | 用户级线程方案 | 开销小；一个阻塞全阻塞；不能多核并行 |
| **一对一** | 1 用户线程 → 1 内核线程 | 内核级线程方案 | 并行、阻塞灵活；线程多开销大 |
| **多对多** | n 用户线程 → m 内核线程 | 组合/两级模型 | 取长补短；实现复杂 |

> **【考点】** 多对多模型怎么取长补短：既保留用户级线程切换快、可定制的优点，又利用内核级线程实现并行和灵活阻塞。  
> **【考点】** 多对一：一个线程阻塞会导致整个进程阻塞；不能利用多核。  
> **【考点】** 一对一：每个用户线程对应一个内核线程，能并行，但线程多时内核开销大。

### 7.6 线程的生命周期（补充）

线程也有创建、就绪、运行、阻塞、终止等状态，但线程状态通常由线程库或内核管理。考试若问“线程有没有生命周期”，答案是：有，但线程的状态转换和进程类似，具体实现依赖线程模型。

## 8. 高频考点速记

1. **进程是程序的一次执行**；程序静态，进程动态。
2. **PCB 是进程存在的唯一标志**，常驻内存，由内核维护。
3. 进程实体＝程序段＋数据段＋PCB。
4. **并发是交替，宏观同时；并行是同一时刻真正同时。**
5. 状态转换：**阻塞不能直接运行；就绪不能直接阻塞；阻塞 → 就绪要被动唤醒。**
6. 运行 → 阻塞主动；阻塞 → 就绪被动；运行 → 就绪被动；block/wakeup 成对。
7. 原语不可中断，保证原子性。
8. 进程通信：共享存储最快但需同步；消息传递解耦；管道半双工；信号异步通知。
9. **线程是 CPU 调度执行基本单位**；进程是资源分配单位。
10. 同进程线程共享代码、数据、堆、文件、地址空间；私有寄存器、栈、PC、TCB。
11. 用户级线程：切换快、可移植，但一个阻塞全进程挂起，同一进程内不能多核并行。
12. 内核级线程：可并行、阻塞灵活，但切换开销大。
13. 多线程模型：多对一、一对一、多对多。
14. 进程切换要保存/恢复 CPU 上下文；同进程线程切换通常比进程切换轻。
15. PCB 组织方式：链接方式、索引方式（补充）。
16. 父子进程终止：级联终止或托孤（补充）。

### 8.1 常见考法

- **选择题**：判断“并发/并行”“就绪/阻塞转换”“PCB 是否是唯一标志”“用户级/内核级线程特点”等说法是否正确。
- **简答题**：进程与程序的区别；PCB 的作用与内容；进程五状态及转换；进程通信四种方式；用户级/内核级线程优缺点；多线程模型。
- **分析题**：给一段进程状态变化，判断主动/被动、是否合法；给一个多线程场景，判断采用哪种模型。

## 9. 易错点纠正

| 常见误区 | 正确说法 |
|---|---|
| 并发是同一时刻，并行是一段时间交替 | **反了。** 并发是一段时间内交替，宏观同时；并行是同一时刻多个处理机真正同时。 |
| 进程就是程序 | 程序静态，进程动态；一个程序可对应多个进程。 |
| PCB 是程序的一部分 | PCB 是内核数据结构，不属于用户程序；进程实体包含 PCB。 |
| 阻塞可以直接变运行 | 必须先变就绪，再等调度。 |
| 就绪可以直接变阻塞 | 进程必须先运行，才能发起 I/O/等待事件。 |
| 阻塞是别人把进程阻塞的 | 阻塞是进程主动的；唤醒是被动的。 |
| 线程都有自己独立的地址空间 | 同进程线程共享地址空间；进程之间才独立。 |
| 用户级线程可以在多核上并行 | 同一进程的用户级线程不能；内核只把进程当一个调度单位。多个进程可以并行，但一个进程内的用户级线程不能同时跑在多个 CPU 上。 |
| 线程切换一定比进程切换快 | 同进程线程切换通常更轻；跨进程线程切换仍可能涉及地址空间切换。 |
| 管道是全双工 | 经典管道是半双工；同一时刻通常单向。 |
| 共享存储不需要同步 | 共享存储最快，但必须同步互斥。 |
| 信号可以传大量数据 | 信号携带信息少，适合通知事件，不适合传大量数据。 |
| 进程永远是 CPU 调度基本单位 | 传统 OS 中进程是调度单位；引入线程后，线程是 CPU 调度和执行单位，进程是资源分配单位。看题目语境。 |
| PCB 只保存程序计数器 | CPU 上下文包括寄存器、PC、栈指针等，不只是 PC。 |
| 进程终止时子进程一定终止 | 取决于系统：可级联终止，也可托孤。 |
| 挂起就是终止 | 挂起只是换出到外存，PCB 还在；终止是进程结束。 |
| “程序对操作系统不透明”是教材术语 | 这是比喻。教材更常说：操作系统通过 PCB 管理进程，不需要理解程序语义。 |

## 10. 收尾一句话

**进程是戏班，PCB 是班牌；线程是演员，TCB 是小本子；五道门管状态，四块金牌管原语，四条传信路管合作，三种分身术管线程。**

下一幕，管理员要让这些戏班公平、高效地上台——这就是“调度”。
