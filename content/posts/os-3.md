# 第三幕 · 金苹果、臭鸡蛋与青铜锁

> **给小朋友的话：**
> 上一幕，马库斯学会了安排戏班上台。这一幕，他要学会安排戏班使用道具。有些道具，一次只能让一个戏班使用；有些戏班，必须等待另一个戏班把东西送到，才能开演。不要害怕，东方三博士又来了。
>
> 故事里会出现一些“小规则牌”，用最简单的步骤写出剧组应该怎么做。
>
> **给大朋友的话：**
> 第三幕对应“同步与互斥”。故事之后的“长大了后您会怎么叙述这个故事”部分，按照教材严格化，重点纠正草稿中“同步与异步”的混淆，并且补齐互斥锁、信号量、生产者与消费者、读者与写者、组互斥、哲学家进餐和管程。

---

## 第一场 道具房里的乱子

赏戏大会结束后的第二天，马库斯还没有来得及喝一口水，道具房就乱成了一团。

《金苹果》的剧组跑过来，说：“我们的金苹果不见了！”

马库斯翻开借据，发现金苹果被《狼奶》的剧组借走了。《狼奶》的剧组说，他们只是把金苹果借去当“狼奶里的金苹果”，演完忘记归还。

《金苹果》的演员只好从厨房抓了一只大公鸡，抱上台去。观众先是一愣，随后笑得前仰后合。大力士抱着公鸡，一本正经地说：“这就是金苹果！”台下有人喊：“那明明是一只公鸡！”

马库斯还没有来得及休息，《落寞贵族阿波罗》的剧组又来了。

“我们的臭鸡蛋呢？”导演问，“我们要十二个臭鸡蛋，摆成一排，才能演出阿波罗的落寞！”

马库斯打开道具箱，里面只剩下三个臭鸡蛋，而且其中两个已经被压碎了。原来，另一个剧组借走了九个臭鸡蛋，去演“臭鸡蛋大战”，还踩碎了一地。

开演的时候，阿波罗的演员看着三个臭鸡蛋，怎么也落寞不起来。观众笑得直拍椅子。

皇帝奥古斯都一世在包厢里拍案而起：“马库斯！再出一次这样的乱子，你就去扫马厩！”

马库斯垂头丧气地回到后台。他想：“金苹果、勇者的剑、恶龙的头套、十二个臭鸡蛋……这些东西，怎么一借就乱？”

就在这时，三位博士又来了。他们看了看道具房，又看了看马库斯，说：“这一幕，我们讲同步与互斥。”

## 第二场 白板演员与四条金规矩

“纠正一个说法。”高个子博士说，“马库斯，你是不是听人说过，这一幕叫‘同步与异步’？”

马库斯点点头。

“这个说法不准确。”博士说，“异步说的是剧组的推进速度不可预知，今天快，明天慢。异步是并发剧场的常态。我们要解决的是同步与互斥。”

“有些道具，一次只能让一个剧组使用，这叫**临界资源**。使用临界资源的那段剧情，叫**临界区**。”

“例如金苹果、勇者的剑、恶龙的头套、十二个臭鸡蛋。一个剧组正在使用的时候，另一个剧组不能同时使用。”

胖博士补充：“金苹果只有一只，勇者的剑只有一把，恶龙的头套只有一个，臭鸡蛋也只有十二个。它们都是临界资源。”

马库斯问：“那我应该怎么管理呢？”

安静的博士说：“你可以招聘一位白板演员。让他站在道具房门口，手里拿着一面小旗，胸前挂着一块白板。”

“哪个剧组要使用临界道具，就到他那里登记。白板演员挥一下旗，表示‘道具房有人要用，暂时不借’。这个登记和挥旗的过程，叫**进入区**。”

“剧组拿到道具，进去使用，这段剧情叫**临界区**。”

“用完了，剧组出来，白板演员把旗子放下，在进出记录上写下‘已经用完’，这叫**退出区**。”

“剩下的剧情，叫**剩余区**。”

马库斯问：“那四条金规矩是什么？”

博士竖起四根手指：

“第一，**空闲让进**。道具房空着，有剧组要用，就让它进去。”

“第二，**忙则等待**。道具房里面有人，其他剧组必须在外面等待。”

“第三，**有限等待**。不能让一个剧组等待到天荒地老。每个想进去的剧组，都应该在有限的时间里进去。”

“第四，**让权等待**。等待不到的剧组不要占着舞台一遍遍询问。它应该下台，去候场区或者阻塞队列，把舞台让给别人。”

马库斯把四条金规矩写在白板上，觉得自己已经明白了。

但是，具体应该怎么让白板演员挥旗，才不会出错呢？

博士拿出一张小规则牌，挂在白板旁边：

```text
想进道具房：
    如果 小旗已经举起：
        在门外等待
    否则：
        举起小旗
        进入道具房
        使用关键道具
        放下小旗
```

这张小卡说明：举旗和检查都属于“进入区”，使用道具属于“临界区”，放下旗子属于“退出区”。

## 第三场 一枚金币与两枚金币

马库斯拿来一枚金币。

“金币正面朝上，表示 A 剧组可以进去。金币反面朝上，表示 B 剧组可以进去。”他说，“A 用完，把金币翻到反面。B 用完，把金币翻到正面。”

“这叫**单标志法**。”博士说，“它确实能够保证一次只有一个剧组进去。但是，如果 A 剧组改了戏，不再需要金苹果，金币还留在正面，B 剧组就永远进不去。它违反了空闲让进，还让 B 剧组在门口忙等。”

马库斯挠挠头：“一枚不够，那就两枚！”

他给 A 剧组和 B 剧组各发一枚金币。金币正面朝上，表示“我想进去”。

“A 剧组查看 B 剧组的金币。如果 B 剧组的金币是反面，A 剧组就把自己的金币翻到正面，随后进去。B 剧组也这样做。”

“这叫**双标志法，检查在设置之前**。”博士说，“问题来了。如果 A 剧组和 B 剧组同时看到对方的金币是反面，随后同时把自己的金币翻到正面，两个剧组就会同时冲进道具房。金苹果被撞成了苹果酱。”

“那我把顺序调过来！”马库斯说，“每个剧组把自己的金币翻到正面之后，查看对方的金币。”

“这叫**双标志法，设置在检查之前**。”博士说，“这回更糟。A 剧组和 B 剧组都把自己的金币翻到正面，随后都看见对方的金币是正面，于是都等待对方先放下。两个剧组互相瞪着对方，谁也不进去，门口乱成一团。”

马库斯快要哭出来了：“一枚也不行，两枚也不行，那应该怎么办？”

博士把两枚金币的规则也画成小卡：

```text
单标志法：
    正面朝上：A 可以进
    A 用完：把金币翻到反面，表示轮到 B
    反面朝上：B 可以进
    B 用完：把金币翻到正面，表示轮到 A
    问题：A 不进去，B 就永远等待

双标志法，检查在设置之前：
    A：看 B 的金币；B 不想进，A 就翻到正面进去
    B：看 A 的金币；A 不想进，B 就翻到正面进去
    问题：两个人同时看，同时翻到正面，就会同时进去

双标志法，设置在检查之前：
    A：翻到正面；看 B 的金币
    B：翻到正面；看 A 的金币
    问题：两个人都翻到正面，都等待对方翻回反面，就会死锁
```

## 第四场 彼得森的旗帜

“不要着急。”高个子博士说，“雅典学院的彼得森有一个办法。”

“还是两枚金币，再加一面小旗。”博士说，“每个剧组想进去的时候，把自己的金币翻到正面，随后把小旗转向对方，表示‘我让你优先’。接着检查：如果对方也想进去，并且小旗正指着对方，自己就等待；否则就进去。”

“如果两个剧组都想进去，小旗只会指向其中一个。被指着的那一个进去，另一个等待。里面的剧组出来之后，把金币翻到反面，外面的剧组才能进去。”

“如果一个剧组不想进去，它的金币是反面，另一个剧组不用等待，直接进去。”

马库斯试了试。果然，两个剧组不再同时冲进道具房了。

“这叫**彼得森算法**。”博士说，“它满足互斥，满足空闲让进，也满足有限等待。但是，它有一个毛病。等待的剧组在门口不停地查看金币、查看小旗，转来转去，占着舞台的时间。这叫**忙等**，不满足让权等待。”

“能不能让等待的剧组去睡觉，等待有人叫它再起来？”马库斯问。

“可以。”博士说，“那就要请出更厉害的帮手。”

博士把彼得森的规则也画成小卡：

```text
每个剧组想进道具房：
    把自己的金币翻到正面
    把小旗转向对方
    如果 对方也翻到正面，并且小旗正指着对方：
        在门外等待
    否则：
        进入道具房
        使用关键道具
        把金币翻回反面
```

小卡的意思：两个人都想进的时候，小旗只会指向一个人；被指着的人等待，另一个人进。等待的人一直在看金币和小旗，所以还是“忙等”。

## 第五场 青铜锁与钥匙

胖博士带着马库斯去集市吃羊肉焖饭。

马库斯把道具房的烦心事说给饭铺老板听。老板是一位满脸胡须的希伯来人，他哈哈大笑：“就为这件事情？你买一个青铜柜子，配一把青铜锁，再配一把唯一的钥匙。谁要使用里面的东西，就把钥匙给他。没有钥匙的人，在外面等待。”

马库斯拍了拍额头：“对啊！金币、小旗也是道具，管理道具的规矩本身也需要被管理。软件的办法过于复杂，我可以做一把坚固的锁！”

他买回青铜柜、青铜锁和一把钥匙。

“剧组要进道具房，就向管理员申请钥匙。管理员查看钥匙在不在。如果在，就交给它；如果不在，就让它等待。剧组用完，把钥匙还回来。申请和归还都要敲铜锣，也就是原子操作。”

“这叫**互斥锁**。”博士说，“锁只有两种状态：锁住和打开。申请锁和释放锁必须是原子操作。”

但是，新的问题来了。

有一个剧组在台上演戏，演到一半需要金苹果。它派了一个演员去问：“有钥匙吗？”管理员说：“没有。”它又派一个演员去问，还是没有。它派了十个演员，问了十次，都没有。演员们在台上跑来跑去，观众以为他们在演“传令兵大赛”。

“这就是**自旋**。”博士说，“拿不到锁的剧组一直询问，一直等待，浪费舞台时间。如果临界区很短，自旋还可以。如果等待的时间很长，就应该让剧组去候场区睡觉，等待钥匙回来之后叫醒它。”

马库斯说：“那我还需要一个等候室。”

“对。”博士说，“钥匙架和等候室，合起来就是**信号量**。”

博士给青铜锁也画了一张小卡：

```text
要进道具房：
    如果 钥匙在架子上：
        拿走钥匙
        进入道具房
        使用关键道具
        还回钥匙
    否则：
        在门口等待

自旋的办法：
    一直问“有钥匙吗？”
    有钥匙就拿走，没有就继续问

阻塞的办法：
    没有钥匙就去长椅上睡觉
    有人还钥匙的时候，叫醒一个等待的人
```

小卡说明：一直问是“自旋”，会浪费舞台时间。去长椅上睡觉才是“让权等待”。

## 第六场 钥匙架与信号量

马库斯做了一个大钥匙架，上面挂着一排钥匙，旁边有一本账簿和一条等候长椅。

“账簿上记一个数字，表示还有多少把钥匙。长椅上坐着等待钥匙的剧组。”博士说，“另外定两条规矩：”

“第一条，**P 操作**。剧组来要钥匙，把账簿上的数字减一。如果减完以后数字小于零，说明没有钥匙了，这个剧组就坐到长椅上，进入阻塞状态。”

“第二条，**V 操作**。剧组还钥匙，把数字加一。如果加完以后数字小于等于零，说明长椅上还有人在等待，就叫醒一个。”

“P 操作和 V 操作都要敲铜锣，不能被打断。”

马库斯问：“数字小于零，应该怎么理解？”

“数字大于等于零的时候，它表示还有多少把钥匙可以使用。数字小于零的时候，它的绝对值表示有多少个剧组在等待。”博士说，“例如数字是负三，就是有三个剧组坐在长椅上。”

“这叫**信号量**。”博士说，“数字的初值是几，就表示一开始有几把钥匙。初值为一，它可以当互斥锁使用。初值为 N，它可以管理 N 个相同的道具。初值为零，它可以用来做同步。”

马库斯用信号量管理金苹果。金苹果只有一只，信号量初值为一。他又用信号量管理十二个臭鸡蛋。臭鸡蛋有十二个，信号量初值为十二。剧组拿到钥匙才能进道具房，拿不到就坐到长椅上等待。这一回，没有人再在台上跑来跑去了。

“可是，”马库斯问，“如果两个剧组要合作，一个负责制作道具，一个负责使用道具，应该怎么办？”

“那就用信号量做**同步**。”博士说。

博士把钥匙架的规矩画成小卡：

```text
P(钥匙)：
    数字减一
    如果 数字小于零：
        坐到长椅上，进入阻塞状态

V(钥匙)：
    数字加一
    如果 数字小于等于零：
        叫醒长椅上的一个剧组

数字大于等于零：还有多少把钥匙可以用
数字小于零：绝对值就是有多少个剧组在等
```

## 第七场 道具交付处

剧场后面新盖了一个道具交付处，里面有 N 个格子。道具制作组把做好的道具放进格子，演出组从格子里取走道具。

“这个交付处，就是**生产者与消费者**问题。”博士说，“制作组是生产者，演出组是消费者。格子是缓冲区，容量为 N。”

“规矩有三条。第一，制作组不能把道具放进已经放满的格子。第二，演出组不能从空格子里取走道具。第三，同一时刻只能有一个剧组在交付处里放或者取。”

马库斯拿出三个信号量：

- `empty`，初值为 N，表示还有多少个空格子；
- `full`，初值为零，表示已经放了多少个道具；
- `mutex`，初值为一，表示交付处的互斥访问权。

“制作组进场，执行 P(empty)，等待一个空格子。执行 P(mutex)，取得交付处的钥匙。放好道具，执行 V(mutex)，归还钥匙。最后执行 V(full)，告诉演出组‘多了一个满格子’。”

“演出组进场，执行 P(full)，等待一个满格子。执行 P(mutex)，取得钥匙。取走道具，执行 V(mutex)，归还钥匙。最后执行 V(empty)，告诉制作组‘多了一个空格子’。”

马库斯照着做了。可是，演出组的组长把最后一个操作写成了 V(full)。

“错了！”博士说，“演出组取走一个道具，格子变空了，应该归还一个空位，所以是 V(empty)。你写成 V(full)，等于告诉制作组‘又多了一个满格子’。空格子的数量永远不会增加，制作组很快就不敢再放了，交付处就堵住了。”

马库斯赶紧改过来。

博士又说：“还有一个顺序要注意。制作组如果让 P(mutex) 排在 P(empty) 前面，万一格子全满，它拿着钥匙等待空格子，演出组进不来，也取不走道具，两边就卡住了。所以，P(empty) 要排在 P(mutex) 前面。演出组也一样，P(full) 要排在 P(mutex) 前面。”

马库斯问：“那 V(mutex) 和 V(full)、V(empty) 的顺序呢？”

“通常让 V(mutex) 排在 V(full) 或者 V(empty) 前面。”博士说，“这样，被叫醒的剧组一进门就能拿到钥匙，不会刚醒又被钥匙挡住。顺序颠倒一般不影响正确性，但是会增加不必要的等待。”

马库斯把交付处的规矩写下来。交付处终于顺畅了。

博士把交付处的正确规则画成小卡：

```text
制作组：
    P(empty)   等待一个空格子
    P(mutex)   拿交付处的钥匙
    放道具
    V(mutex)   还钥匙
    V(full)    喊“多了一个满格子”

演出组：
    P(full)    等待一个满格子
    P(mutex)   拿交付处的钥匙
    取道具
    V(mutex)   还钥匙
    V(empty)   喊“多了一个空格子”
```

小卡下面画了一个红色的叉：

```text
演出组取走道具以后写 V(full)：错！
空位不会增加，制作组最后会停下来等待空位。
```

## 第八场 剧本库里的读者与写者

剧场的剧本库也出了问题。

很多剧组要读同一本剧本，读者可以一起读。但是，皇帝请来的剧作家要修改剧本。修改的时候，不能有任何人读，否则会读到一半新、一半旧。

“这叫**读者与写者**问题。”博士说，“读者共享，写者独占。读者和写者之间要互斥，写者和写者之间也要互斥。”

马库斯问：“那应该怎么记录谁在读呢？”

“用一个计数器 `read_count`，记录当前有几个读者。再用一个互斥信号量 `rmutex` 保护这个计数器。再用一个信号量 `wmutex` 保护剧本，让写者和读者不能同时使用。”

“读者进门，执行 P(rmutex)。如果 `read_count` 是零，说明自己是第一个读者，就执行 P(wmutex)，把剧本锁住，不让写者进来。随后 `read_count` 加一，执行 V(rmutex)，开始读。”

“读完了，执行 P(rmutex)，`read_count` 减一。如果减到零，说明自己是最后一个读者，就执行 V(wmutex)，把剧本让出来。最后执行 V(rmutex)。”

“写者进门，执行 P(wmutex)。写完了，执行 V(wmutex)。”

马库斯照着做了。读者们很高兴，可以一起读。可是，剧作家在门口等待了很久，读者一批接着一批，他始终进不去。

“这是**读者优先**的毛病。”博士说，“只要还有读者，写者就可能一直等待。这叫**写者饥饿**。如果皇帝的剧作家很重要，你可以让写者优先。写者一来，就把新读者挡在门外。现有的读者走完，写者先进。”

马库斯想了想，说：“那我给写者发一张‘优先牌’。”

“可以。”博士说，“不过，写者优先也可能让读者饥饿。公平的做法是排一个先来后到的队，或者让读者和写者轮流进入。具体使用哪一种，要看剧场的目标。”

马库斯把读者优先和写者优先都记在本子上，准备让皇帝自己选择。

博士把剧本库的规则画成小卡：

```text
读者：
    登记“我要读”
    如果 我是第一个读者：
        锁住剧本，不让写者进
    读者人数加一
    读剧本
    读者人数减一
    如果 我是最后一个读者：
        打开剧本锁

写者：
    锁住剧本
    修改剧本
    打开剧本锁
```

小卡说明：读者可以一起读，写者要独占。读者一直来，写者就可能一直等待，这叫“写者饥饿”。

## 第九场 两组施工队

剧场要扩建，来了两组施工队：A 队和 B 队。

A 队的工人可以一起施工。B 队的工人也可以一起施工。但是，A 队和 B 队不能同时施工，否则两边会把墙砌歪。

“这叫**组互斥**。”博士说，“A 队内部共享，B 队内部共享，A 队和 B 队之间互斥。”

马库斯给 A 队准备了 `countA` 和 `mutexA`，给 B 队准备了 `countB` 和 `mutexB`，又准备了一把公共的 `site`。

“A 队的第一个工人进场，执行 P(mutexA)，发现 `countA` 是零，就执行 P(site)，把公共工地锁住。随后 `countA` 加一，执行 V(mutexA)，开始施工。”

“A 队的第二个工人进场，执行 P(mutexA)，发现 `countA` 不是零，就不需要再拿公共锁。`countA` 加一，执行 V(mutexA)，也进去施工。”

“A 队的最后一个工人离开，执行 P(mutexA)，`countA` 减一。如果减到零，就执行 V(site)，把公共工地让出来。最后执行 V(mutexA)。”

“B 队也这样做，只是使用 `countB` 和 `mutexB`。”

马库斯试了试。A 队的人一起施工，B 队的人一起施工。两组不会混在一起。可是，如果 A 队正在施工，B 队的第一个工人会拿着 `mutexB` 在门口等待待公共锁，B 队的其他人就进不了 `mutexB`，只能在更外面等待。

“这不算错。”博士说，“B 队本来就要等待 A 队完工，只是 B 队的其他人不能在门口排队，只能在外面等待。如果你想让 B 队的人也能到门口等待，可以把公共锁的申请放到 `mutexB` 外面。不过，取得公共锁之后要重新检查计数，代码会更复杂。考试一般按你现在这种写法来考。”

马库斯点点头，把这段记在本子上。

博士把两组施工的规则画成小卡：

```text
A 队工人：
    如果 我是第一个 A 队工人：
        锁住公共工地
    A 队人数加一
    施工
    A 队人数减一
    如果 我是最后一个 A 队工人：
        打开公共工地

B 队工人：
    和 A 队一样，只是用 B 队的人数。
```

小卡说明：A 队内部可以一起施工，B 队内部也可以一起施工，两组不能同时施工。

## 第十场 哲学家的宴席

皇帝请了五位哲学家吃饭。圆桌上摆着五根筷子，每两位哲学家之间一根。每位哲学家要吃一口饭，必须同时拿起左右两根筷子。

五位哲学家同时伸手，每个人都拿起了左边的筷子，随后都等待右边的筷子。结果，五个人各拿一根，谁也不肯放下，谁也吃不到饭。

“这就是**哲学家进餐**问题。”博士说，“每个人占有一根筷子，等待另一根。五个人围成一个圈，形成**循环等待**，于是**死锁**了。”

马库斯问：“那应该怎么办？”

“办法有三个。”博士说。

“第一个，最多只让四位哲学家同时拿筷子。”博士说，“五根筷子，四个人抢，至少有一个人能够拿到两根。你用一个信号量 `picker`，初值为四。每位哲学家拿筷子之前执行 P(picker)，吃完再执行 V(picker)。”

“第二个，给哲学家编号。偶数号从左边开始拿筷子，奇数号从右边开始拿筷子。这样，大家拿筷子的方向不一致，就不会围成一个等待圈。”

“第三个，只有左右两根筷子都空闲的时候，才允许拿。可以用一个互斥锁，把‘拿两根筷子’的动作保护起来；也可以使用同时等待两根筷子的信号量，一次等待两根。”

马库斯照着第一个办法做了。五位哲学家不再死锁，饭桌终于安静下来。

“不过，”博士提醒，“不死锁不等于不饥饿。如果信号量的等候队列不公平，某个哲学家可能一直抢不到筷子。考试如果问‘是否饥饿’，要看信号量的实现和调度策略。”

博士把三种办法画成三张小卡：

```text
办法一：最多四个人拿筷子
    拿筷子之前：P(picker)
    拿起左右两根筷子
    吃饭
    放下两根筷子
    V(picker)

办法二：奇偶编号
    偶数号：左筷在前，右筷在后
    奇数号：右筷在前，左筷在后

办法三：两根筷子一起拿
    如果 左右两根都空闲：
        拿起两根
    否则：
        一根也不拿
```

## 第十一场 总管与等候牌

面对金币、小旗、青铜锁、钥匙架、计数器和筷子，马库斯感到头昏脑涨。

“这些东西都能使用，”他说，“可是太容易出错了。有没有更简单的办法？”

“有。”安静的博士说，“你可以请一位总管。”

“总管把道具房、账簿、钥匙、等候室全都管理起来。剧组要借道具，不用自己挥旗、拿钥匙、记账。它只要向总管提出请求。总管一次只接待一个剧组，所以道具房天然就是互斥的。”

“如果剧组要的东西暂时没有，总管就给它一张**等候牌**，让它到旁边的椅子上等待。等待道具准备好了，总管再叫它。”

“这叫**管程**。”博士说，“管程把共享数据和对共享数据的操作封装在一起。任何时刻最多只有一个剧组在管程里面。管程里面的**条件变量**，就是等候牌。`wait` 表示坐下等待，`signal` 表示叫醒一个。”

博士把总管的规矩画成小卡：

```text
总管办公室：
    一次只让一个剧组进来

剧组要东西：
    如果要的东西没有：
        拿一张等候牌，坐到椅子上等待
    如果要的东西有了：
        总管叫醒一个拿等候牌的人

条件变量的两个动作：
    wait：坐下等待，并且把办公室让出来
    signal：叫醒一个等待的人
```

马库斯请了一位总管。总管上任以后，道具房再也没有出现金苹果被换成大公鸡、臭鸡蛋被踩碎的事情。

皇帝很高兴，赏了总管一袋蜜饯。

弄臣又凑过来，叮叮当当地问：“如果两个剧组一个等待对方先走，另一个也等待对方先走，应该怎么办？”

马库斯的脸又白了。

博士们笑了：“那是死锁的故事，下一幕再讲。”

## 1. 进程同步与互斥的基本概念

### 1.1 进程的异步性

并发进程以各自独立的速度推进，执行顺序不可预知。这就是进程的异步性。异步性是并发系统的固有性质。

多个进程并发访问共享数据的时候，执行结果可能取决于它们相对的执行顺序。这种情况称为竞争条件。竞争条件是引入同步机制的根本原因。

### 1.2 同步与互斥

同步指合作进程之间的直接制约关系。一个进程需要等待另一个进程产生数据或者发出信号，才能继续执行。例如，生产者把产品放入缓冲区之后，消费者才能取出产品。

互斥指竞争进程之间的间接制约关系。多个进程共享同一个临界资源，任何时刻只允许一个进程进入临界区。例如，两个进程不能同时使用同一台打印机。

需要特别说明，这一幕的主题是同步与互斥，并非同步与异步。异步性描述并发进程的推进方式。同步与互斥描述协调这些进程的规则。竞争关系对应互斥。合作关系对应狭义的同步。广义的进程同步包括同步和互斥。

| 对比 | 同步 | 互斥 |
|---|---|---|
| 制约关系 | 直接制约 | 间接制约 |
| 来源 | 进程合作 | 进程竞争共享资源 |
| 典型例子 | 生产者与消费者 | 打印机、共享变量 |
| 信号量初值 | 0 或者 N | 1 |
| 目标 | 保证执行顺序 | 保证临界区排他访问 |

### 1.3 临界资源与临界区

临界资源是一次只允许一个进程使用的资源。进程访问临界资源的那段代码称为临界区。为了管理临界区，通常把代码划分为四个部分：

| 部分 | 作用 |
|---|---|
| 进入区 | 检查是否可以进入临界区，并且申请进入权限 |
| 临界区 | 访问临界资源 |
| 退出区 | 释放临界资源，允许其他进程进入 |
| 剩余区 | 其余代码 |

进入区包含检查与申请的动作。退出区包含释放的动作。容易混淆的地方是：挥旗本身属于进入区，清除标志属于退出区。进入区并不等于挥旗之前的代码。

### 1.4 同步机制应当遵循的四个准则

1. 空闲让进：临界区空闲的时候，一个请求进入的进程应当立即进入。
2. 忙则等待：已经有进程在临界区的时候，其他请求进入的进程必须等待。
3. 有限等待：请求进入的进程应当在有限时间内进入临界区，不能无限等待。
4. 让权等待：进程不能进入临界区的时候，应当释放处理机，进入阻塞状态，避免忙等。

有限等待关注等待时间的上界。让权等待关注等待期间是否占用处理机。一个算法可以满足有限等待，但是不满足让权等待，Peterson 算法就是例子。

这四个准则并不要求每一种实现都同时满足。软件算法通常在让权等待上作出妥协。硬件指令和阻塞式信号量可以更好地满足让权等待。考试常问某一个算法满足哪些准则，需要逐条判断。

## 2. 软件实现方法

### 2.1 单标志法

单标志法设置一个公共的轮转变量 `turn`，用它指示当前允许进入临界区的进程。

```c
int turn = 0; // 0 表示 P0 可以进入，1 表示 P1 可以进入

void P0() {
    while (turn != 0) {
        // 忙等
    }
    // 临界区
    turn = 1;
    // 剩余区
}

void P1() {
    while (turn != 1) {
        // 忙等
    }
    // 临界区
    turn = 0;
    // 剩余区
}
```

单标志法能够保证互斥。两个进程不可能同时通过 `while` 循环。它的问题是强制两个进程轮流进入临界区。如果 P0 不再需要进入临界区，`turn` 仍然停留在 0，P1 就会一直等待。这种情况违反空闲让进，也违反有限等待。等待的进程一直在检查 `turn`，不满足让权等待。

### 2.2 双标志法

双标志法为每个进程设置一个标志 `flag[i]`，表示该进程是否希望进入临界区。根据检查与设置的先后顺序，分为两种写法。

#### 2.2.1 检查在设置之前

```c
bool flag[2] = {false, false};

void P0() {
    while (flag[1]) {
        // 忙等
    }
    flag[0] = true;
    // 临界区
    flag[0] = false;
    // 剩余区
}

void P1() {
    while (flag[0]) {
        // 忙等
    }
    flag[1] = true;
    // 临界区
    flag[1] = false;
    // 剩余区
}
```

两个进程可能同时检查到对方的标志为 `false`，随后都把自己的标志设置为 `true`，并且都进入临界区。这种写法不能保证互斥。

#### 2.2.2 设置在检查之前

```c
bool flag[2] = {false, false};

void P0() {
    flag[0] = true;
    while (flag[1]) {
        // 忙等
    }
    // 临界区
    flag[0] = false;
    // 剩余区
}

void P1() {
    flag[1] = true;
    while (flag[0]) {
        // 忙等
    }
    // 临界区
    flag[1] = false;
    // 剩余区
}
```

两个进程可能同时把自己的标志设置为 `true`，随后都检查到对方的标志为 `true`，于是都无限等待。这种写法可能发生死锁，违反空闲让进和有限等待。它也不能满足让权等待。

### 2.3 Peterson 算法

Peterson 算法使用两个标志和一个轮转变量，适合两个进程。

```c
bool flag[2] = {false, false};
int turn = 0;

void P0() {
    flag[0] = true;
    turn = 1;
    while (flag[1] && turn == 1) {
        // 忙等
    }
    // 临界区
    flag[0] = false;
    // 剩余区
}

void P1() {
    flag[1] = true;
    turn = 0;
    while (flag[0] && turn == 0) {
        // 忙等
    }
    // 临界区
    flag[1] = false;
    // 剩余区
}
```

Peterson 算法满足互斥、空闲让进和有限等待。它不满足让权等待，因为等待的进程一直在检查标志和轮转变量，属于忙等。Peterson 算法假设对 `flag` 和 `turn` 的读写具有原子性。实际系统可能需要内存屏障来防止指令重排序。

### 2.4 软件方法小结

| 方法 | 互斥 | 空闲让进 | 有限等待 | 让权等待 | 主要问题 |
|---|---|---|---|---|---|
| 单标志法 | 满足 | 不满足 | 不满足 | 不满足 | 强制轮流，可能无限等待 |
| 双标志法（检查在设置之前） | 不满足 | 无法保证 | 无法保证 | 不满足 | 两个进程可能同时进入 |
| 双标志法（设置在检查之前） | 满足 | 不满足 | 不满足 | 不满足 | 可能死锁 |
| Peterson 算法 | 满足 | 满足 | 满足 | 不满足 | 忙等，依赖原子读写 |

## 3. 硬件实现方法

### 3.1 中断屏蔽

在单处理机系统中，进程进入临界区之前可以关闭中断，退出临界区之后打开中断。关闭中断期间，进程不会被切换，于是可以保证互斥。

这种方法不适合多处理机系统。关闭一个处理机的中断不能阻止其他处理机访问共享资源。关闭中断的时间也不能太长，否则会影响系统响应。用户态进程通常没有关闭中断的权限。

### 3.2 测试并设置指令

测试并设置指令是一条原子指令。它读取锁的旧值，把锁设置为 `true`，并且返回旧值。

```c
bool TestAndSet(bool *lock) {
    bool old = *lock;
    *lock = true;
    return old;
}

void lock(bool *lock) {
    while (TestAndSet(lock)) {
        // 忙等
    }
}

void unlock(bool *lock) {
    *lock = false;
}
```

测试并设置指令能够保证互斥。它通常用于实现自旋锁。等待的进程反复执行指令，不满足让权等待。它也不能保证有限等待，因为多个进程可能一直竞争，某个进程可能长期抢不到锁。

### 3.3 交换指令

交换指令原子地交换寄存器和一个内存单元的内容。它也可以用来实现锁。

```c
void lock(bool *lock) {
    bool key = true;
    while (key) {
        Swap(&key, lock);
    }
}

void unlock(bool *lock) {
    *lock = false;
}
```

交换指令与测试并设置指令类似。它能够保证互斥，但是可能忙等，并且不能保证有限等待。

### 3.4 硬件方法的评价

硬件原子指令解决了标志和轮转变量的原子访问问题，是自旋锁的基础。它们通常需要与阻塞机制配合，才能满足让权等待。现代处理器还提供比较并交换指令，用于实现更复杂的锁和原子操作。

## 4. 互斥锁

### 4.1 基本思想

互斥锁是一个二值变量，只有“锁住”和“打开”两种状态。进程进入临界区之前申请锁，退出临界区之后释放锁。申请和释放必须是原子操作。

### 4.2 自旋锁与阻塞锁

自旋锁在锁被占用的时候，让进程反复检查锁的状态。它适合临界区很短、处理机数量较多的场合。自旋锁会让等待的进程占用处理机，不满足让权等待。

阻塞锁在锁被占用的时候，把进程放入等待队列，并且让进程进入阻塞状态。锁释放的时候，唤醒一个等待进程。阻塞锁满足让权等待，但是需要上下文切换，开销比自旋锁大。

### 4.3 互斥锁与信号量的区别

互斥锁通常有所有者，只有加锁的进程才能解锁。信号量没有所有者，任何进程都可以执行 V 操作。互斥锁只有两种状态。信号量有一个计数值，可以表示多个资源。

互斥锁适合实现临界区的互斥访问。信号量既可以实现互斥，也可以实现同步。

## 5. 信号量

### 5.1 定义

信号量由一个整数值和一个等待队列组成。对信号量的操作只有 P 操作和 V 操作，二者都是原子操作。P 操作也称为等待操作，V 操作也称为释放操作。

- P 操作：把计数值减一。如果计数值小于零，调用进程进入等待队列，并且进入阻塞状态。
- V 操作：把计数值加一。如果计数值小于等于零，从等待队列中唤醒一个进程。

计数值大于等于零的时候，它表示当前可用的资源数量。计数值小于零的时候，它的绝对值表示等待队列中的进程数量。

### 5.2 信号量的类型

| 类型 | 初值 | 用途 |
|---|---|---|
| 互斥信号量 | 1 | 实现临界区的互斥访问 |
| 计数信号量 | N | 管理 N 个相同的资源 |
| 同步信号量 | 0 | 实现进程之间的先后顺序 |

### 5.3 用信号量实现互斥

```c
semaphore mutex = 1;

P(mutex);
// 临界区
V(mutex);
// 剩余区
```

同一个进程的 P 操作和 V 操作必须成对出现。P 操作在进入区执行，V 操作在退出区执行。互斥信号量的初值为 1，保证任何时刻只有一个进程进入临界区。

### 5.4 用信号量实现同步

同步信号量的初值通常为 0。一个进程完成某个动作之后执行 V 操作，另一个进程在需要等待的地方执行 P 操作。

```c
semaphore ready = 0;

// 进程 A
produce();
V(ready);

// 进程 B
P(ready);
consume();
```

进程 B 在执行 P(ready) 的时候，如果 `ready` 的值为 0，就会阻塞，直到进程 A 执行 V(ready)。这样，消费动作一定发生在生产动作之后。需要说明的是，同步信号量的 P 操作和 V 操作可以跨进程配对。生产者执行 V(ready)，消费者执行 P(ready)，两者共同完成一次同步。

#### 5.4.1 前趋关系（补充）

前趋图用有向边表示进程之间的先后关系。如果进程 A 必须在进程 B 之前执行，就为边 A→B 设置一个初值为 0 的信号量 S。进程 A 执行完之后执行 V(S)。进程 B 在开始执行之前执行 P(S)。这样，B 会等待 A 完成。多条前趋边需要为每条边设置一个信号量。

### 5.5 信号量的实现要点

阻塞式信号量满足让权等待。自旋式信号量不满足让权等待。P 操作和 V 操作的顺序非常重要。顺序错误可能导致死锁或者资源计数错误。信号量的编程难度较高，容易出现 P/V 不配对、顺序错误、重复释放等问题。

## 6. 经典同步问题

### 6.1 生产者与消费者问题

#### 6.1.1 问题描述

生产者把产品放入缓冲区，消费者从缓冲区取出产品。缓冲区有 N 个槽位。生产者不能向满缓冲区放入产品。消费者不能从空缓冲区取出产品。任何时刻只允许一个进程访问缓冲区。

#### 6.1.2 信号量设置

| 信号量 | 初值 | 含义 |
|---|---|---|
| `empty` | N | 空槽位的数量 |
| `full` | 0 | 满槽位的数量 |
| `mutex` | 1 | 缓冲区的互斥访问权 |

#### 6.1.3 正确代码

```c
semaphore empty = N;
semaphore full = 0;
semaphore mutex = 1;

void producer() {
    while (true) {
        item = produce();
        P(empty);
        P(mutex);
        put(item);
        V(mutex);
        V(full);
    }
}

void consumer() {
    while (true) {
        P(full);
        P(mutex);
        item = take();
        V(mutex);
        V(empty);
        consume(item);
    }
}
```

#### 6.1.4 常见错误

第一类错误出现在消费者的 V 操作。消费者取走产品之后，缓冲区多出一个空槽位，应当执行 V(empty)。如果写成 V(full)，空槽位的数量不会增加，生产者最终会因为 P(empty) 而永久阻塞。

第二类错误出现在 P 操作的顺序。生产者如果让 P(mutex) 排在 P(empty) 前面，缓冲区满的时候，生产者持有互斥锁并且等待空槽位。消费者无法进入缓冲区取走产品，双方发生死锁。消费者如果让 P(mutex) 排在 P(full) 前面，缓冲区空的时候，消费者持有互斥锁并且等待产品，生产者无法进入缓冲区放入产品，双方同样发生死锁。因此，P(empty) 必须排在 P(mutex) 之前，P(full) 必须排在 P(mutex) 之前。

第三类问题出现在 V 操作的顺序。通常让 V(mutex) 排在 V(full) 或者 V(empty) 之前。这样，被唤醒的进程进入缓冲区的时候，互斥锁已经释放，不会刚被唤醒又因为互斥锁而阻塞。顺序颠倒一般不影响正确性，但是会增加不必要的上下文切换。

#### 6.1.5 与故事中的交付处比喻的对应关系

空槽位对应交付处的空格子。满槽位对应已经放好道具的格子。互斥信号量对应交付处的钥匙。制作组对应生产者。演出组对应消费者。这个比喻可以帮助记忆，但是考试答题应当使用信号量的标准术语。

### 6.2 读者与写者问题

#### 6.2.1 问题描述

多个读者可以同时读取同一个文件。写者修改文件的时候，不能有读者或者其他写者同时访问文件。读者和写者之间互斥。写者和写者之间互斥。读者和读者之间可以共享。

#### 6.2.2 读者优先的代码

```c
int read_count = 0;
semaphore rmutex = 1;
semaphore wmutex = 1;

void reader() {
    while (true) {
        P(rmutex);
        if (read_count == 0) {
            P(wmutex);
        }
        read_count++;
        V(rmutex);
        read();
        P(rmutex);
        read_count--;
        if (read_count == 0) {
            V(wmutex);
        }
        V(rmutex);
    }
}

void writer() {
    while (true) {
        P(wmutex);
        write();
        V(wmutex);
    }
}
```

`rmutex` 保护 `read_count`。`wmutex` 保护文件，保证读者和写者不能同时访问文件，也保证两个写者不能同时访问文件。第一个读者进入的时候执行 P(wmutex)，最后一个读者离开的时候执行 V(wmutex)。

#### 6.2.3 读者优先与写者饥饿

读者优先的代码中，只要还有读者在读取文件，写者就必须等待。如果读者不断到达，写者可能永远得不到执行机会。这种情况称为写者饥饿。

写者优先的一种做法是增加一个排队信号量。写者到达的时候取得排队信号量，随后等待 `wmutex`。新读者到达的时候也必须取得排队信号量。这样，写者等待期间，新读者会被挡在门外。写者取得 `wmutex` 之后释放排队信号量。现有读者结束之后，写者进入。写者优先也可能导致读者饥饿。公平的做法是使用先来先服务的队列，或者让读者和写者轮流进入。

### 6.3 组互斥问题

A 组和 B 组共享一个施工场地。A 组的成员可以同时施工。B 组的成员也可以同时施工。A 组和 B 组不能同时施工。

```c
int countA = 0;
int countB = 0;
semaphore mutexA = 1;
semaphore mutexB = 1;
semaphore site = 1;

void A() {
    while (true) {
        P(mutexA);
        if (countA == 0) {
            P(site);
        }
        countA++;
        V(mutexA);
        construct();
        P(mutexA);
        countA--;
        if (countA == 0) {
            V(site);
        }
        V(mutexA);
    }
}

void B() {
    while (true) {
        P(mutexB);
        if (countB == 0) {
            P(site);
        }
        countB++;
        V(mutexB);
        construct();
        P(mutexB);
        countB--;
        if (countB == 0) {
            V(site);
        }
        V(mutexB);
    }
}
```

这段代码保证 A 组内部共享、B 组内部共享、两组之间互斥。A 组的第一个成员取得公共场地锁，最后一个成员释放公共场地锁。B 组同理。

需要说明一个细节。A 组的第一个成员持有 `mutexA` 等待 `site` 的时候，A 组的其他成员会被挡在 `mutexA` 外面。这样，A 组只有一个成员在等待公共场地，其他成员无法提前排队。这种写法不会造成死锁，但是会降低组内的并发度。如果希望同组其他成员也能排队，可以在等待 `site` 之前释放 `mutexA`，取得 `site` 之后重新获取 `mutexA`，并且检查计数。考试通常按上面的标准写法作答。

### 6.4 哲学家进餐问题

五位哲学家围坐在圆桌旁。每两位哲学家之间有一根筷子。每位哲学家需要同时拿起左右两根筷子才能进餐。如果五位哲学家都拿起左边的筷子，随后等待右边的筷子，就会形成循环等待，发生死锁。

#### 6.4.1 错误解法

```c
void philosopher(int i) {
    while (true) {
        P(chopstick[i]);
        P(chopstick[(i + 1) % 5]);
        eat();
        V(chopstick[i]);
        V(chopstick[(i + 1) % 5]);
    }
}
```

五位哲学家同时执行 P(chopstick[i])，每个人都拿到左边的一根筷子。随后每个人都执行 P(chopstick[(i + 1) % 5])，等待右边的一根筷子。五根筷子都已经被人拿着，没有人愿意释放，于是发生死锁。

#### 6.4.2 解法一：限制同时拿筷子的人数

```c
semaphore chopstick[5] = {1, 1, 1, 1, 1};
semaphore picker = 4;

void philosopher(int i) {
    while (true) {
        P(picker);
        P(chopstick[i]);
        P(chopstick[(i + 1) % 5]);
        eat();
        V(chopstick[i]);
        V(chopstick[(i + 1) % 5]);
        V(picker);
    }
}
```

最多允许四位哲学家同时尝试拿筷子。五位哲学家竞争五根筷子，至少有一位哲学家能够拿到两根筷子。这样就不会出现五位哲学家各持一根筷子并且互相等待的局面。这个解法避免了死锁，但是不能保证每个哲学家都不会饥饿。信号量的等待队列是否公平，会影响有限等待。

#### 6.4.3 解法二：奇偶编号

```c
void philosopher(int i) {
    while (true) {
        if (i % 2 == 0) {
            P(chopstick[i]);
            P(chopstick[(i + 1) % 5]);
        } else {
            P(chopstick[(i + 1) % 5]);
            P(chopstick[i]);
        }
        eat();
        V(chopstick[i]);
        V(chopstick[(i + 1) % 5]);
    }
}
```

偶数号哲学家从左边开始拿筷子。奇数号哲学家从右边开始拿筷子。相邻两位哲学家拿筷子的顺序相反，不会形成所有哲学家都持有左边筷子并且等待右边筷子的循环。这个解法破坏了循环等待条件。

#### 6.4.4 解法三：一次取得两根筷子

一种办法是使用同时等待型信号量，一次申请两根筷子。如果两根筷子不能同时满足，哲学家一根也不拿。这种办法破坏了请求与保持条件。

另一种办法是用互斥锁保护两次 P 操作：

```c
void philosopher(int i) {
    while (true) {
        P(mutex);
        P(chopstick[i]);
        P(chopstick[(i + 1) % 5]);
        V(mutex);
        eat();
        V(chopstick[i]);
        V(chopstick[(i + 1) % 5]);
    }
}
```

用互斥锁保护两次 P 操作，可以把“拿两根筷子”变成一个串行动作。这个办法避免多个哲学家同时各持一根筷子并且互相等待，从而避免死锁。它的缺点是拿筷子的过程被串行化，并发度降低。

#### 6.4.5 死锁与饥饿的区别

死锁是多个进程互相等待对方持有的资源，永远无法继续执行。饥饿是某个进程长期得不到资源，但是系统仍然在推进。哲学家进餐问题的主要风险是死锁。限制人数、奇偶编号、一次取得两根筷子这三种思路都可以避免死锁。它们不一定能避免饥饿。判断是否饥饿，需要看信号量的等待队列是否公平，以及调度策略是否保证有限等待。

## 7. 管程

### 7.1 管程的定义

管程是一种高级同步机制。它把共享数据和对共享数据的操作封装在一起。任何时刻最多只有一个进程在管程内部执行。管程的互斥由编译器或者运行时系统自动保证。程序员不需要显式编写 P/V 操作来保护共享数据。

管程由四个部分组成：

1. 管程的名称。
2. 局部于管程的共享数据结构。
3. 对共享数据结构进行操作的一组过程。
4. 初始化语句。

### 7.2 条件变量

条件变量用于管程内部的同步。每个条件变量有一个等待队列。条件变量支持两种基本操作：

- `wait(c)`：调用进程在条件变量 `c` 上等待，进入等待队列，并且释放管程。其他进程可以进入管程。
- `signal(c)`：从条件变量 `c` 的等待队列中唤醒一个进程。如果没有进程在等待，这个操作不产生效果。

条件变量与信号量不同。条件变量没有计数值，不能像信号量那样表示资源数量。条件变量的 `wait` 和 `signal` 必须配合管程的互斥使用。

### 7.3 管程的语义

管程有两种常见的语义。

- Hoare 语义：执行 `signal` 的进程立即放弃管程，被唤醒的进程立即进入管程执行。执行 `signal` 的进程随后等待，直到被唤醒的进程离开管程或者再次等待。
- Mesa 语义：执行 `signal` 的进程继续执行，被唤醒的进程进入就绪队列。被唤醒的进程重新获得管程之后，需要重新检查条件。大多数实际系统采用 Mesa 语义。

在 Mesa 语义下，条件等待通常写成循环：

```c
while (!condition) {
    c.wait();
}
```

这样，被唤醒的进程会重新检查条件，避免条件不满足的时候继续执行。

### 7.4 用管程解决生产者与消费者问题

```c
monitor ProducerConsumer {
    int buffer[N];
    int count = 0;
    int in = 0;
    int out = 0;
    condition notFull;
    condition notEmpty;

    void put(item) {
        while (count == N) {
            notFull.wait();
        }
        buffer[in] = item;
        in = (in + 1) % N;
        count++;
        notEmpty.signal();
    }

    item get() {
        while (count == 0) {
            notEmpty.wait();
        }
        item = buffer[out];
        out = (out + 1) % N;
        count--;
        notFull.signal();
        return item;
    }
}
```

生产者调用 `put` 的时候，如果缓冲区已经满了，就在 `notFull` 上等待。消费者调用 `get` 的时候，如果缓冲区为空，就在 `notEmpty` 上等待。放入产品之后，生产者唤醒一个在 `notEmpty` 上等待的消费者。取出产品之后，消费者唤醒一个在 `notFull` 上等待的生产者。管程自动保证同一时刻只有一个进程在 `put` 或者 `get` 内部执行。

### 7.5 管程与信号量的比较

| 对比 | 管程 | 信号量 |
|---|---|---|
| 抽象层次 | 高 | 低 |
| 互斥 | 自动保证 | 程序员用 P/V 保证 |
| 同步 | 条件变量 | 信号量 |
| 编程难度 | 较低 | 较高 |
| 错误风险 | 较低 | 容易出现 P/V 错误 |
| 语言支持 | 需要编译器或者运行时支持 | 多数系统提供 |

管程把互斥和同步封装起来，降低了编程难度。信号量更加灵活，但是更容易出错。考试中常见的问法是“管程如何保证互斥”“条件变量的 wait 和 signal 有什么作用”“管程与信号量有什么区别”。

## 8. 高频考点速记

1. 进程异步性描述并发进程推进速度不可预知。竞争条件指执行结果依赖相对执行顺序。
2. 同步是合作进程之间的直接制约关系。互斥是竞争进程之间的间接制约关系。广义的进程同步包括同步和互斥。
3. 这一幕的主题是同步与互斥，并非同步与异步。异步性不是互斥的对立面。
4. 临界资源一次只允许一个进程使用。临界区是访问临界资源的代码段。
5. 临界区代码分为进入区、临界区、退出区、剩余区四个部分。
6. 四个准则：空闲让进、忙则等待、有限等待、让权等待。
7. 单标志法保证互斥，但是强制轮流，违反空闲让进和有限等待，并且忙等。
8. 双标志法（检查在设置之前）可能让两个进程同时进入，违反互斥。
9. 双标志法（设置在检查之前）可能死锁，违反空闲让进和有限等待。
10. Peterson 算法满足互斥、空闲让进、有限等待，但是不满足让权等待。
11. 硬件方法包括中断屏蔽、测试并设置指令、交换指令。硬件原子指令是自旋锁的基础。
12. 自旋锁忙等，适合短临界区和多处理机。阻塞锁满足让权等待，但是有上下文切换开销。
13. 互斥锁通常有所有者。信号量没有所有者，任何进程都可以执行 V 操作。
14. 信号量由计数值和等待队列组成。计数值大于等于零表示可用资源数量，小于零的绝对值表示等待进程数量。
15. 信号量分为互斥信号量、计数信号量、同步信号量。初值分别为 1、N、0。
16. 阻塞式信号量满足让权等待。自旋式信号量不满足让权等待。
17. 生产者与消费者的信号量为 `empty=N`、`full=0`、`mutex=1`。
18. 消费者取走产品之后执行 V(empty)，并非 V(full)。
19. 生产者与消费者问题中，P(empty) 必须排在 P(mutex) 之前，P(full) 必须排在 P(mutex) 之前。
20. 读者与写者问题中，`rmutex` 保护 `read_count`，`wmutex` 保护文件。
21. 读者优先可能导致写者饥饿。写者优先可能导致读者饥饿。公平队列可以避免饥饿。
22. 组互斥问题中，第一个成员取得公共锁，最后一个成员释放公共锁。
23. 哲学家进餐问题的错误解法可能发生死锁。限制人数、奇偶编号、一次取得两根筷子这三种思路可以避免死锁。
24. 死锁是互相等待、永远无法推进。饥饿是长期得不到资源，但是系统仍然在推进。
25. 管程自动保证互斥。条件变量的 `wait` 会释放管程，`signal` 唤醒一个等待进程。
26. Hoare 语义下，`signal` 立即转移管程。Mesa 语义下，`signal` 之后被唤醒的进程需要重新检查条件。
27. 互斥使用时，同一个进程的 P 操作和 V 操作必须成对出现。同步使用时，一个进程的 V 操作可以和另一个进程的 P 操作配对。顺序错误可能导致死锁或者计数错误。
28. 前趋图用信号量实现时，每条前趋边设置一个初值为 0 的信号量。前趋进程执行 V 操作，后继进程执行 P 操作。

### 8.1 常见考法

- **选择题**：判断某个算法满足哪些准则；判断 P/V 操作之后计数值的含义；判断死锁与饥饿的区别；判断管程与信号量的区别。
- **简答题**：同步与互斥的区别；临界区的四个部分；四个准则；Peterson 算法；互斥锁与信号量的区别；管程与条件变量。
- **代码题**：找出生产者与消费者代码中的错误；写出读者与写者代码；写出组互斥代码；补全哲学家进餐的解法。
- **综合题**：用信号量解决某个实际问题；用管程解决生产者与消费者问题；分析某个解法是否死锁、是否饥饿。

## 9. 易错点纠正

| 常见误区 | 正确说法 |
|---|---|
| 把这一幕称为“同步与异步” | 这一幕的主题是同步与互斥。异步是并发进程的推进方式，不是互斥的对立面。 |
| 竞争关系就是异步 | 竞争关系对应互斥。异步性描述进程推进速度不可预知。 |
| 进入区是挥旗之前的剧情 | 进入区包含检查和申请进入权限的动作，挥旗属于进入区。 |
| 清除进入区标志属于进入区 | 清除标志属于退出区。 |
| 单标志法提前退出只会让另一个进程忙等 | 单标志法强制轮流进入。一个进程不再进入的时候，另一个进程可能永远等待，违反空闲让进和有限等待。 |
| 双标志法两个标志都是反面，两个进程都会进入 | 检查在设置之前的写法可能让两个进程同时进入，违反互斥。 |
| 双标志法调换顺序只是违反有限等待 | 设置在检查之前的写法可能发生死锁，违反空闲让进和有限等待。 |
| Peterson 算法满足让权等待 | Peterson 算法使用忙等，不满足让权等待。它满足互斥、空闲让进和有限等待。 |
| 信号量至少需要多把钥匙 | 信号量的初值可以是 1、N 或者 0。初值为 1 的时候，它表示一把钥匙；初值为 N 的时候，它表示 N 个资源；初值为 0 的时候，它用于同步。 |
| 消费者取走产品后执行 V(full) | 消费者取走产品后应当执行 V(empty)，表示增加一个空槽位。 |
| 同步就是给出一个钥匙 | 同步信号量的初值通常为 0。生产者执行 V 操作发出信号，消费者执行 P 操作等待信号。 |
| 读者与写者代码中的 count 就是读者计数 | 读者计数应当用 `read_count` 表示。`rmutex` 保护 `read_count`，`wmutex` 保护文件。 |
| 最后一个读者释放的是 rmutex | 最后一个读者释放 `wmutex`，允许写者进入。`rmutex` 在退出区仍然要释放。 |
| A/B 组代码中第一个成员持有组内锁等待公共锁是错误 | 这种写法不会死锁，但是会降低组内并发度。可以在等待公共锁之前释放组内锁，取得公共锁之后重新检查计数。 |
| 哲学家进餐的“最多四人”解法一定不会饥饿 | 这个解法避免死锁，但是不能保证不饥饿。是否饥饿取决于信号量队列是否公平以及调度策略。 |
| V(picker)l 是合法语句 | 这是笔误，应当是 V(picker);。 |
| 管程就是信号量 | 管程是高级同步机制，自动保证互斥。信号量是低级同步机制，需要程序员编写 P/V。 |
| 条件变量的 signal 一定会唤醒一个进程 | 如果没有进程在等待，signal 不产生效果。 |
| 管程的 wait 不释放管程 | 管程的 wait 会释放管程，让其他进程进入。 |
| 死锁和饥饿是一回事 | 死锁是互相等待、永远无法推进。饥饿是长期得不到资源，但是系统仍然在推进。 |

## 10. 收尾一句话

**关键道具要互斥，合作关系要同步；软件方法有金币和小旗，硬件方法有锁和钥匙；信号量有账簿和长椅，管程有总管和等候牌。** 下一幕，如果两个剧组互相等待对方手里的道具，那就是死锁的故事。
